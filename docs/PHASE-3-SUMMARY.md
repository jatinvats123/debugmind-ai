## What was built

**An animated cast of a full run**, at the top of the README. It shows the whole
loop: failing test → ranked hypotheses → sandboxed probe → fix → *a failed
attempt with its forced revert and recorded learning* → verified fix → green
suite. The failure path is the part worth watching, and it happens to be in the
recorded run rather than being staged.

**A sample report** (`docs/examples/sample-debug-report.md`) and the structured
log behind it, from a real run: three attempts, four hypotheses, two probes, two
recorded learnings.

**A README that leads with measured results** rather than description, and states
the limitations in the README itself rather than a file nobody opens.

## Why SVG and not a GIF

The roadmap asked for a GIF via asciinema. This machine has no `asciinema`, no
`agg`, and no `ffmpeg`; the one `convert` on PATH is Windows' filesystem
converter, not ImageMagick. The project also forbids paid or native
dependencies, which rules out the canvas-based GIF encoders.

So the cast is generated by a ~150-line zero-dependency script
(`scripts/make-demo-svg.js`) that parses the raw ANSI capture and emits an
animated SVG. Animated SVG renders inline on GitHub — the same mechanism the
widely used typing-SVG badges rely on. It is also smaller, sharper at any zoom,
and diffable, which a GIF is not.

**Honesty note:** I generated and structurally validated the SVG (well-formed,
66 frame groups, no unescaped entities, no stray escape codes) but I cannot
verify GitHub's rendering from this machine. If it does not animate in your
browser, the fix is to install `asciinema` + `agg` and re-record; the raw capture
is committed for exactly that reason.

---

## The honesty constraint on the demo

A demo is the easiest place in a project to lie, so two rules:

1. **Every frame contains lines the run actually printed.** Nothing is retyped or
   staged. Long stretches are time-compressed by advancing several lines per
   frame, and the complete raw transcript is committed beside the cast
   (`docs/media/demo-raw.txt`) so the cast can be checked against its source.
2. **The demo is the offline replay**, not a live run. It needs no API key and
   reproduces byte-for-byte from the Phase 1 cassette, so what a reviewer sees is
   exactly what they get from `npm run agent:offline`.

## Reassessment checkpoint

The roadmap asks me to stop here and confirm the state of the evidence.

**The benchmark ran for real.** 24 fixture×arm runs, every one executed against a
live model. `BENCHMARK.md` contains no placeholders — the `TODO(run-required)`
machinery exists and works, and there is currently nothing left for it to mark.
Per-run records are committed under `benchmark/results/` and the report can be
regenerated from them with `npm run bench:report` without spending a token.

**The numbers are not flattering everywhere, and that is deliberate.** The
regression reduction I predicted did not appear. The control never touched the
writable test files. The resolution-rate edge is one fixture on n=12. The
guardrails cost about 22% more tokens. All of that is in `BENCHMARK.md`, the
Phase 2 summary, and now the README.

**One number is missing on purpose.** Cost per fix is reported as *unpriced*,
because `agent/pricing.json` ships with rates unset. Token counts are measured
and real; I would rather report no dollar figure than a stale one.
